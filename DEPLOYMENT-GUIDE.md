# E-Shop — Public Preview Deployment Kit

## Scope and precautions

This is a **public preview**, not a production-ready shop accepting real payments.
It was prepared against the current GitHub `main` versions of selected files. Check
local edits before replacing them. The kit does not touch the mobile project.

Files included:
- `render.yaml` — two Render services, API and Vite SPA, pointing to a separate Neon Postgres database.
- `backend/src/app.ts` — production browser CORS allowlist via `FRONTEND_ORIGIN`.
- `backend/src/modules/payments/payment.routes.ts` — removes payment simulator route in production.
- `backend/scripts/bootstrap-admin.ts` — one-time admin account and role bootstrap using your own secret.

**Before publication:** do not use the repository's sample `prisma db seed` on a
public database: it contains a known default administrator login. Do not commit
`backend/.env`, `.env.*`, Neon database strings, or JWT/admin secrets. If a password
found in any committed example was ever real, rotate it. Review the repository for
other hard-coded credentials.

## 1. Prepare and test locally

From `ecommerce-system`:

```powershell
cd frontend
npm ci
npm run build
cd ..\backend
npm ci
npx prisma generate
npm run build
```

If either build fails, resolve that exact error before deployment.
Make a Git commit for the changes to the **existing website project**; never push
real secrets. Avoid committing stale local web changes from outdated GitHub code.

## 2. Create persistent Postgres with Neon

Create a new Postgres project at https://console.neon.tech/ . Copy its secure,
SSL-enabled connection URI from the dashboard. Keep it private. Your local
PostgreSQL data does NOT migrate automatically. For a safe public preview, start
with an empty schema and add products deliberately, or plan a reviewed export
of catalog records only (never blindly copy customer data).

## 3. Install the schema and bootstrap roles on your laptop

Use a separate PowerShell window in `backend`, where Prisma and `tsx` are
installed. Do NOT overwrite your existing local `.env` with the production DB URL.

```powershell
$env:DATABASE_URL = Read-Host 'Paste Neon DATABASE_URL (kept out of command history)'
$env:ADMIN_EMAIL = Read-Host 'Admin email'
$securePassword = Read-Host 'Strong unique admin password (16+ chars)' -AsSecureString
$env:ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', $securePassword).Password
npx prisma migrate deploy
npx tsx scripts/bootstrap-admin.ts
Remove-Item Env:DATABASE_URL,Env:ADMIN_EMAIL,Env:ADMIN_PASSWORD
```

Only do this against a NEW, EMPTY database. Make sure you aren't accidentally
pointing at your existing local database. Neon may provide direct and pooled
connection strings; verify which Neon connection string is suitable for migrations.

## 4. Create Render services

At https://dashboard.render.com/ connect your GitHub repo and create a
**Blueprint** from the root-level `render.yaml`. Render will ask for:

API (`eshop-api-preview`):
- `DATABASE_URL`: the Neon URL
- `FRONTEND_ORIGIN`: your real Render static site HTTPS origin, no trailing slash
- `JWT_SECRET`: generated by Render; do not replace with a guess

Static site (`eshop-web-preview`):
- `VITE_API_URL`: your real Render API HTTPS URL ending in `/api`

Example format only, not actual URLs:
- `FRONTEND_ORIGIN=https://YOUR-WEB-SERVICE.onrender.com`
- `VITE_API_URL=https://YOUR-API-SERVICE.onrender.com/api`

These two URLs are different values, and Render chooses the final subdomains.
If a Blueprint fails because the other service URL isn't yet known, first deploy
the backend and frontend with temporary placeholders, then set both real values
in the Render dashboard and redeploy. The Vite variable is read **at build time**:
changing it requires a new static-site build/deploy.

Render's free web plan has no pre-deploy command, so the API Start Command is
`npx prisma migrate deploy && npm start`, idempotently applying migrations first.

The backend `PORT` uses Render's port (default 10000); don't hardcode 5000 in
Render. The static Vite build output is `frontend/dist`. The SPA rewrite keeps
React Router routes working after refresh.

## 5. Verify

- Open the API root: `https://YOUR-API.onrender.com/`
- Open public catalog: `https://YOUR-API.onrender.com/api/products`
- Open front end: `https://YOUR-WEB.onrender.com/`
- In browser Developer Tools > Network, verify product calls go to your HTTPS API
  and never `localhost`.
- Check search, product details, theme, authentication, admin permissions,
  cart and orders in a TEST account.
- Verify `POST /api/payments/:id/simulate` is **not** available in production.

## Not yet safe for commercial use

1. Product image uploads currently use local Multer disk storage; free Render
   restarts/redeploys erase the files. Use Cloudinary, S3/R2, or another persistent
   object store and migrate existing product images before expecting permanence.
2. Simulation is disabled, but **real payment processing is not integrated**. Do
   not accept money or show simulated payments as collected.
3. Audit authentication, authorization, rate limiting, validation, error handling,
   webhook verification, checkout/idempotency, and backup/restore before a true
   customer-facing launch.
4. Render free web services sleep after inactivity; Neon Free has usage limits.
   These are intended for public testing, not availability guarantees.
